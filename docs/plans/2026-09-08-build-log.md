## Log

- Bootstrap: docs-only commit on `main`; implementation on `feat/mcp-server-foundation`.

- Auth foundation (commit 30f5b44): OIDC proxy boots; harness happy path passes on first run.
- fastmcp/mcp findings while building (all verified in the installed 4.0.3 / 2.2.0):
  - `mcp` `RevocationRequest` requires `client_secret` (no default) -> public clients get 400 on `/revoke`. Own handler in `auth.py` (commit 16515f9). Worth an upstream issue.
  - fastmcp's `AuthorizationHandler` never reads `resource`, so `OAuthProxy.authorize`'s RFC 8707 check is unreachable. Own pre-check on `/authorize` (trailing slash tolerated, other path -> `invalid_target` redirect).
  - `OIDCProxy` does not plumb `revocation_endpoint` from discovery; set `_upstream_revocation_endpoint` ourselves.
  - The upstream verifier fills `AccessToken.client_id` from `azp`; the SDK revocation guard compares it with the MCP client id -> we overwrite it with the Luca JWT's `client_id`.
  - Local port 8080 is owned by Docker Desktop on IPv6 (`localhost` resolves to `::1` first): dev server moved to 8765.

Observations: firm admin `ygreen@company.com` sees 371 businesses -> `list_businesses` gained `query`/`limit`/`offset`; the API returns the full account subtree whatever `levels_deep` says -> flattener enforces depth; `taxes/vat/determination` on bu-2 is all zeros with `missing_vat_accounts` warnings -> tool explains it in `notes`.

- Token lifetimes (`tests/e2e/expiry_suite.py`, mock access 330 s / Luca access 40 s): expired Luca token -> 401 -> client refresh rotates both tokens; upstream token inside the 300 s threshold -> exactly one transparent upstream refresh with the pinned scope set, none on the next call; after the IdP revokes all refresh tokens the still-valid upstream token keeps serving calls. Observed: fastmcp retries the failed transparent refresh 3x per call while the upstream refresh token is dead (harmless here; would add token-endpoint traffic on Auth0 in that rare state).

## Self-review (2026-09-08, end of day)

Final evidence: `tests/e2e/tools_suite.py` 27/27, `tests/e2e/harness.py auth-suite` 17/17, `tests/e2e/expiry_suite.py` PASS, real Claude Code CLI login/tools/logout PASS. 24 commits on `feat/mcp-server-foundation`; `ant-rai` and `ant-liebre-api` untouched.

Deliberate trade-offs to revisit
- `offline_access` is advertised in `scopes_supported` (the spec says SHOULD NOT) because Claude Code requests only advertised scopes and Auth0 issues refresh tokens only for it. Week-1 change: `luca:read` advertised, upstream scope forced server-side (`extra_authorize_params` already does this).
- Consent mode `remember` (signed cookie per client + redirect URI) instead of `always`; local/dev may set `off`.
- In-memory OAuth state store: one instance only; every restart logs users out. `REDIS_URL` switches to Redis (one line) but has not been exercised.
- fastmcp 4.0.3 is pinned and the proxy subclass touches internals (`_hash_token`, store attributes, `_upstream_client_secret`, `_resource_url`). Upgrading requires re-running the auth suite; the tests would catch drift.
- Money values are passed through as the API's JSON numbers; Luca never computes with them except the informational `balance_check` sums (rounded to cents).
- Caches: tenant context 5 min per identity, period entry list 60 s, chart-of-accounts index 5 min. Liebre re-authorises every call, so the caches only affect freshness of listings, never access.
- `platform_url` is the platform root until frontend routes are known.

Untested until the real Auth0 application exists

The mock IdP mirrors Auth0's token shape and endpoints, not its tenant settings.
- Codex, Cursor, claude.ai and VS Code clients (only the automated harness and Claude Code were run).

Behaviours worth knowing
- fastmcp retries a failed transparent upstream refresh three times per call while the upstream refresh token is dead; harmless locally, extra token-endpoint traffic on Auth0 in that rare state.
- `whoami` always reloads the tenant context (two or more Liebre calls); every other tool uses the cache.
- The first `get_journal_entry` for a business/period fetches the full chart of accounts (~450 KB on bu-2, ~0.7 s) to resolve account numbers; later calls hit the index.
- Type errors on tool arguments are rejected by the schema with pydantic's message, not the Luca error envelope.
