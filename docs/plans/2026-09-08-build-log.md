## Dev environment facts (verified)

- Liebre dev API: `https://api-dev.liebre.ai/api/v1`. `bu-2` ("Diaz Curiel Servicios SA de CV", firm `af-2`, sandbox) has 21 open periods `202501`–`202608` (incl. `202513`), 262 journal entries in `202608`, a full chart of accounts (54 top-level accounts), money accounts, customers, SAT archives (`mx.declaracion_mensual_diot` for 2026-07 and others, created 2026-09-05), documents (DIOT PDF, acuse de pago PDF).
- The dev API does not verify token signatures; a locally minted RS256 token whose `email` claim names an existing user passes liebre-api **and** ms-permissions. Test identity: `ygreen@company.com` (`us-2`, firm admin of `af-2`, `allowed` on `bu-2`, business role `manager`). This is the synthetic account used by the API repo's own fixtures. Anand's own address is not a dev user (401 "Error validating user").
- `GET /api/v1/accounting_firms` must be called **without** `Accounting-Firm-ID` (with the header the dev API answers 400 "Accounting-Firm-ID is required for permission check").
- Business routes without the header answer 400 `validation_error` with `errors[0].field == "header -> Accounting-Firm-ID"`.
- `taxes/vat/determination` on bu-2 returns zeros plus `warnings: [{code: missing_vat_accounts, ...}]` (its chart has no VAT sub_sub_types). Tools must surface warnings.
- `declaraciones?year=2026` for bu-2: every month `overdue`, `primary: null`.
- Chart of accounts `levels_deep=1` still returns ~450 KB (nested children are included); the tool must prune server-side.
- Local Auth0 machine-to-machine credentials (rai's env) are used only for seeding; never for user traffic.
- `gcloud` needs an interactive re-login on this machine (`gcloud auth login`), so Cloud Run deployment is deferred; E2E proof is local server + dev API.

## Log

- Bootstrap: docs-only commit on `main`; implementation on `feat/mcp-server-foundation`.

- Auth foundation (commit 30f5b44): OIDC proxy boots; harness happy path passes on first run.
- fastmcp/mcp findings while building (all verified in the installed 4.0.3 / 2.2.0):
  - `mcp` `RevocationRequest` requires `client_secret` (no default) -> public clients get 400 on `/revoke`. Own handler in `auth.py` (commit 16515f9). Worth an upstream issue.
  - fastmcp's `AuthorizationHandler` never reads `resource`, so `OAuthProxy.authorize`'s RFC 8707 check is unreachable. Own pre-check on `/authorize` (trailing slash tolerated, other path -> `invalid_target` redirect).
  - `OIDCProxy` does not plumb `revocation_endpoint` from discovery; set `_upstream_revocation_endpoint` ourselves.
  - The upstream verifier fills `AccessToken.client_id` from `azp`; the SDK revocation guard compares it with the MCP client id -> we overwrite it with the Luca JWT's `client_id`.
  - Local port 8080 is owned by Docker Desktop on IPv6 (`localhost` resolves to `::1` first): dev server moved to 8765.
- Tools (commit 05448c9): six beta tools smoke-tested on bu-2. Observations: firm admin `ygreen@company.com` sees 371 businesses -> `list_businesses` gained `query`/`limit`/`offset`; the API returns the full account subtree whatever `levels_deep` says -> flattener enforces depth; `taxes/vat/determination` on bu-2 is all zeros with `missing_vat_accounts` warnings -> tool explains it in `notes`.
- Amount representation: the Liebre API already serialises money as JSON numbers (floats); tools pass them through unchanged instead of re-encoding as strings. Luca never computes with them.
- Auth suite: 16/17 then 17/17 after fixing a test body that a formatter had moved out from under a string patch (server code was already correct).
