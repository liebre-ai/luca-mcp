## 1. AUTH

### 1.1 End-user authentication: Auth0 bearer JWT, signature NOT verified

`src/auth/validate_user.py:18-61`:
```python
AUTH0_DOMAIN = os.getenv("AUTH0_DOMAIN")  # e.g., "dev-xyz.us.auth0.com"
AUTH0_AUDIENCE = os.getenv("AUTH0_AUDIENCE")  # your API identifier
ALGORITHMS = ["RS256"]

security = HTTPBearer()


def verify_access_token(token: str) -> dict:
    """
    Verifies an Auth0 RS256 JWT access token and returns its claims payload.

    ⚠️  DEVELOPMENT ONLY: JWT signature verification is disabled.
    🔒 TODO: Enable proper JWT verification with JWKS for production.
    """
    try:
        payload = jwt.decode(
            token,
            options={"verify_signature": False},  # ⚠️  DISABLED FOR DEVELOPMENT
            algorithms=ALGORITHMS,
        )
        return payload
    except InvalidTokenError:
        raise


async def validate_user(credentials: HTTPAuthorizationCredentials = Security(security)):
    try:
        access_token = credentials.credentials
        claims = verify_access_token(access_token)
        logger.info(f"Verifying Claims")
        user_account_email = claims["email"] if "email" in claims else None
        # Support both user tokens and machine-to-machine (M2M) tokens.
        # User tokens include an email claim; M2M tokens typically have sub like
        # "<client_id>@clients" and no email.
        subject = claims.get("sub", "")
        if not user_account_email and subject.endswith("@clients"):
            # Treat as service principal. For M2M, skip DB lookup and return a stable id.
            # Downstream code expects a string user_account_id; we use the subject.
            logger.info("Authenticated M2M client credentials token: %s", subject)
            return subject
    except Exception:
        traceback.print_exc()
        raise HTTPException(status_code=401, detail="Invalid authentication token")
```

`src/auth/validate_user.py:63-122` then resolves the user **by email**:
```python
        db = PostgresConnection()
        with db.get_session() as session:
            query = select(user_account).where(
                user_account.c.email == user_account_email
            )
            result = session.execute(query).fetchone()

            if not result:
                raise HTTPException(status_code=404, detail="User not found")

            user_account_id = result.user_account_id

            # Check if this is the first login (user is pending_activation)
            if result.user_account_status == "pending_activation":
                ... update user_account_status="active", insert user_account_change_log ...
        return user_account_id
    except Exception as e:
        traceback.print_exc()
        logger.error(f"Error validating user: {e}")
        raise HTTPException(status_code=401, detail="Error validating user")
```
The 404 for an unknown email is raised inside the `try`, so it is swallowed and re-raised as `401 "Error validating user"`. The dependency returns the `user_account_id` string (e.g. `us-123`) or the M2M subject (`<client_id>@clients`).

Verified facts:
- `AUTH0_DOMAIN` / `AUTH0_AUDIENCE` are read but **never used for validation**. There is no issuer, audience, expiry or signature check. With `verify_signature: False`, PyJWT 2.10.1 (pinned in `requirements.txt`) also skips `exp`/`nbf`/`iat`/`aud`/`iss` verification unless those options are explicitly re-enabled, which they are not. Any well-formed JWT whose `email` claim matches a row in `user_account` is accepted, including expired tokens.
- Git history: the only commit touching this logic is `3c531e0c` ("Security fixes: Remove hardcoded email and sensitive JWT logging"). No JWKS verification work exists anywhere in `src/auth/` for user tokens (JWKS is used only for Google service identity tokens, §1.5).
- Missing `Authorization` header → **403 `{"detail": ... "Not authenticated"}`**, not 401 (FastAPI `HTTPBearer(auto_error=True)`, `.venv/lib/python3.11/site-packages/fastapi/security/http.py:88-90`). A malformed/undecodable token → 401 `Invalid authentication token`.
- Identity claims used: `email` (user tokens) and `sub` (only to detect the `@clients` suffix). No business, firm, role or permission claims are read from the token.
- Real token shape (5 expired dev tokens are committed in `src/auth/validated_tokens.json`; I decoded claim names and non-personal values only): header `alg=RS256`, `typ=JWT`, `kid` present; `iss = "https://dev-vnmixbo7lbxr85ex.us.auth0.com/"`; `aud = ["https://api-dev.liebre.ai/api/v1", "https://dev-vnmixbo7lbxr85ex.us.auth0.com/userinfo"]`; `scope = "openid email"`; `azp` (client id); `iat`/`exp` with `exp - iat = 86400` seconds (24 h); plus `email` and `sub`. How the `email` claim reaches an Auth0 *access* token (Auth0 Action, or the SPA sending an ID token) is not visible in this repo — unverified.
- In-repo OAuth endpoints are dev helpers, not a token service: `GET /api/v1/authorize` (`src/auth/authorize.py:26-51`: Authorization Code + PKCE redirect to `{AUTH0_DOMAIN}/authorize` with `audience=AUTH0_AUDIENCE`, `scope=openid email`; the verifier is written to the file `src/auth/code_verifier.tmp`) and `GET /api/v1/access_token?code=` (`src/auth/access_token.py:15-46`: exchanges the code with `client_secret` + verifier at `{AUTH0_DOMAIN}/oauth/token` and returns Auth0's JSON unchanged). No refresh-token handling. `src/auth/token_storage.py` (file-based token allowlist) and `src/utils/validate_permissions.py` (legacy role check) have **no importers** anywhere in `src/` — dead code.

### 1.3 Business access: the firm × business × user triple

`src/utils/user_account_accounting_firm_business_access.py:11-80` — `validate_user_business_access(accounting_firm_id, business_id, user_account_id)` runs one query over `business ⟕ accounting_firm_business ⟕ accounting_firm_business_user_account` and raises:
- `NotFoundException` (404) `Business {id} not found`;
- `ForbiddenException` (403) `Business {id} is not associated with accounting firm {firm}`;
- `ForbiddenException` (403) `User does not have access to business {id} or accounting firm {firm}` when there is no row with `business_user_account_status == "allowed"`.

It is called **imperatively inside handlers** (198 call sites across 166 endpoint files), always wrapped in `if not user_account_id.endswith("@clients"):`. Nothing applies it centrally; a handler that omits it has no business-level check other than the permission decorator.

### 1.4 Authorization: `@require_permission` → external ms-permissions

`src/utils/permissions/decorator.py:100-331`. Behaviour:
- M2M bypass: `if user_account_id and str(user_account_id).endswith("@clients"): ... return await func(*args, **kwargs)` (`:139-148`). If no `user_account_id` kwarg exists the check is skipped too (`:150-156`).
- Headers are read from the live `Request` object (`_extract_headers_from_kwargs`, `:25-49`; `_get_permission_headers`, `:52-74`); missing `Authorization` or `Accounting-Firm-ID` → 400 `"Authorization and Accounting-Firm-ID headers are required"`, unless the decorator was created with `require_accounting_firm_header=False` (then the check is skipped, `:162-175`).
- Slugs starting with `accounting_firm:` are resolved with `GET {PERMISSIONS_API_BASE_URL}/accounting_firms/{firm}/users/{user}/permissions` (`src/endpoints/permissions/accounting_firm/users_permissions_get_service.py:26-45`). Business slugs use `GET .../businesses/{business_id}/users/{user}/permissions/{permission_id}` (single) or `.../permissions` (several) (`src/endpoints/permissions/business_permissions/users_permissions_get_service.py:40-119, 122-161`). All of them forward the caller's headers verbatim:
  ```python
  def get_only_headers(headers):
      return {
          "Authorization": headers["authorization"],
          "Accounting-Firm-ID": headers["accounting-firm-id"],
      }
  ```
  `PERMISSIONS_API_BASE_URL` defaults to `http://permissions-api:8009/api/v1`; timeout connect 30 s / read 120 s / write 30 s (`src/endpoints/permissions/config.py:11-13`).

- Denial format (`decorator.py:18-22`):
  ```json
  {"detail": {"error": "forbidden", "message": "Permission denied", "errors": [{"field": "body", "type": "forbidden"}]}}
  ```

- `PermissionedRoute` (`src/utils/permissions/route.py`) is inert: the decorator injects hidden `Depends` parameters into the wrapper signature itself (`:311-325`); the knowledge base (l.8963-8968) confirms nobody sets `.dependencies`.

- Coverage: 87 distinct slugs on 267 routes; 181 authenticated routes carry **no** slug (they rely on the triple check or nothing extra). Complete slug list: `routes.json`. Grants (role → slugs) live only in ms-permissions; the local `permission_catalog` table is a registry that app code never reads (`docs/plans/2026-06-17-declaraciones-design.md:26-30`). `GET /api/v1/users/me/permissions` and `GET /api/v1/businesses/{b}/users/me/permissions` resolve `me` to the caller (`users_permissions_get.py:47-53`).

## 2. App wiring

- Entrypoint `src/main.py`. `app = FastAPI(title="Liebre API", version="0.2.0", docs_url="/docs", redoc_url="/redoc", ...)` (`main.py:782-795`); the OpenAPI document is served at the FastAPI default `/openapi.json`, in every environment. Every business router is mounted with `prefix="/api/v1"` (`main.py:1231-1236`); `health` and the `internal` routers are mounted without prefix (`:1223-1228`). Router registration order matters and is commented inline (static paths before `/{id}` catch-alls, `:850-1219`).
- File convention (`.cursor/rules/general.mdc`): one file per endpoint `<module>_<verb>.py` plus `<module>_<verb>_service.py`, SQLAlchemy Core queries, Pydantic models per module, every endpoint declares `accounting_firm_id: str = Depends(validate_accounting_firm_header)`.
- Lifespan (`main.py:494-780`): Sentry init (`SENTRY_ENABLE`, `send_default_pii=True`, SAT-credential scrubbing), APScheduler jobs (FX rates, cache reconciliation, JE embeddings, reimbursement sweep) and several asyncio background workers (cache rebuild, counterparty resolution, backup import, bulk unlink, AR/AP export).
- CORS (`main.py:832-841`): `allow_origins=os.getenv("ALLOWED_ORIGINS","").split(",")`, `allow_credentials=True`, all methods and headers, `expose_headers=["content-disposition"]`. `.env.example` shows origins `http://app-dev.liebre.ai,https://app-dev.liebre.ai`.
- No rate limiting anywhere (grep for slowapi/limiter/ratelimit returns nothing). Limits are only at the ASGI server: `docker-entrypoint.sh` runs hypercorn (default) or uvicorn with 2 workers, keep-alive 75 s, read timeout 3000 s, `--limit-concurrency 80` (uvicorn path).
- Error envelope (`src/utils/exception_handlers.py:27-181`, `:184-233`): every error is
  ```json
  {"detail": {"error": "<bad_request|unauthorized|forbidden|not_found|conflict|unprocessable_entity|internal_server_error|service_unavailable|gateway_timeout>",
              "message": "<text>", "errors": [{"field": "<loc>", "type": "<type>", "message": "<optional>"}], "details": "<optional>"}}
  ```
  Request validation returns 400 `validation_error` for malformed fields and 422 `unprocessable_entity` when an enum value is invalid (`:236-291`). SQL integrity errors map to 409 (unique), 422 (foreign key) or 400 (`:408-467`). Custom exception classes live in `src/utils/exceptions.py`; endpoint helpers `create_validation_error` (422), `create_bad_request_error` (400), `create_not_found_error` (404), `create_conflict_error` (409), `create_unprocessable_content_error` (422) in `src/utils/error_handler.py:399-640`.
- Pagination: **no single convention**. Patterns: `page`/`page_size` (helper defaults 1/20, max 100 in `src/utils/pagination_config.py:8-16`; CFDI batches and progressive JEs use 1/50), `limit`/`offset` (JE search 50/max 200, sat_archives 50/max, AR/AP summaries 50, documents, DIOT-adjacent), keyset `before`/`limit` (`ledger_accounts/{id}/journal_entries`), and many lists that are **not paginated at all** (periods, COA tree, JEs per period, money accounts, statement lines, customers, suppliers, cost centers, tags, employees). Envelopes: `{"data": [...]}` most common; search `{"data", "total"}`; sat_archives `{"data", "pagination": {limit, offset, total, has_more}}`; some return bare lists.
- Conditional GET: only `GET .../periods/{p}/journal_entries/bulk` honours `If-None-Match` and answers 304 (`journal_entries_get_bulk.py:103-112`); `src/utils/etag.py` exists for the COA but no route reads `If-None-Match` for it.
- Long-running semantics: JSON reports come from a period-balance cache and return `status: "processing"` with empty rows while it rebuilds (clients must poll; `trial_balance_get.py:73`, `balance_cache_service.py:36-38`). AR/AP integration exports are async jobs (`202 {job_id, status}` → status → `/download`). CFDI unlink and backup import expose job endpoints. Several reconcile flows poll RAI for up to 48-80 s inside the request.
- OpenAPI quality for tool generation: strong for JSON CRUD (typed Pydantic models, descriptions), weak elsewhere. ~50 operations are untyped `any`/`dict`: every XLSX/XML/PDF export, everything proxied to ms-cfdis (`cfdis/search`, `cfdi_drafts`, `sat-account-classification`; DIOT rows are `extra="allow"` on purpose, KB l.8820-8827), the autopilot PATCH (raw JSON body, `autopilot.py:55-71`). Four duplicate operationIds (`create_user_api_v1_users__post`; enable/disable/resend_invitation — the same router is mounted twice in `main.py:865-866` and `:1084-1085`). The only security scheme is `HTTPBearer`; `Accounting-Firm-ID` shows as a per-operation header parameter; required permissions are not in the spec (use `routes.json`). operationIds are auto-generated and long; descriptions mix Spanish and English.

### 3.9 The SAT side: what is extracted from SAT and where to read it

1. **SAT archives — `GET /businesses/{b}/sat_archives`** (`src/endpoints/sat_archives/`, schema `src/database/ant_sat_archive_schemas.py`; perm `business:documents:view`). Immutable extraction records: table `sat_archive{sat_archive_id (uuid), business_id, sat_archive_extraction_type_id, document_id, requested_at, source='sat', request_data (jsonb), extracted_data (jsonb), schema_version, status ∈ processing|completed|failed}`. Files live in GCS (`SAT_ARCHIVE_GCS_BUCKET`, objects `sat_archives/{business_id}/{sat_archive_id}/...`): at most one `primary_document` and N indexed `evidence` files (`sat_archive_file` → `document_file{file_name, file_type, file_size, sha256, storage_path}`). `extracted_data` and `request_data` are validated against per-type versioned JSON Schemas (`sat_archive_extraction_type_schema.request_data_schema / extracted_data_schema`). Endpoints: `GET .../sat_archives?sat_archive_extraction_type_id&status&requested_from&requested_to&limit=50&offset=0` → `{data:[{sat_archive_id, sat_archive_extraction_type_id, schema_version, requested_at, status, request_data, document_id, has_document, evidence_count, created_at, updated_at}], pagination}`; `GET .../sat_archives/latest?sat_archive_extraction_type_id=` and `GET .../sat_archives/{id}` → full record with `extracted_data`, `document` and `evidences[]`; `GET .../sat_archives/types` and `/types/{type_id}` → catalog `{sat_archive_extraction_type_id, name, requires_primary_document, document_type_id, schema_version}` plus both JSON Schemas; `GET .../sat_archives/{id}/files/{sat_archive_file_id}/download` → bytes (`StreamingResponse`, `Cache-Control: private, no-store`). Writers are `POST/PATCH/DELETE .../sat_archives` (multipart; perm `business:documents:upload`), i.e. an extractor outside this repo (RAI or a SAT/Syncfy job) pushes archives in. The only extraction-type artefact in the repo is `docs/sat_archives/mx.declaracion_mensual_diot.v1.json`; the seeded type ids live in migrations/DB and were not enumerated here. **This is the most likely home of "the documents we extracted last week from SAT"**; its structured `extracted_data` is what an MCP would compare with ledger figures (for example against `taxes/vat/determination/{period}` and `diot/periods/{p}/accounting_baseline`).
2. **Documents — `GET /businesses/{b}/documents`** (`src/endpoints/documents/`, schema `src/database/ant_ms_documents_schemas.py`; perm `business:documents:view`). Per-business document store (bytes in Postgres `document_content` or GCS) with catalog `document_type{id, periodicity none|monthly|annual, allows_update, update_function, external_type}` seeded with 8 `mx.*` types. In code only `mx.declaracion_mensual_impuestos_federales_acuse` is named; the catalog's update-function ids reveal the intended set: `updateMxComplianceOpinion` (opinión de cumplimiento), `updateMxTaxStatusCertificate` (constancia de situación fiscal), `updateMxMonthlyPaymentReference`, `updateMxAnnualPaymentReference` (líneas de captura) (`documents_registry.py:60-94`). Endpoints: `GET .../documents?document_type&source&year&month&limit&offset=0` → `{data:[{id, file_name, file_type, file_size, document_type, source, year, month, created_at, updated_at}]}`; `GET .../documents/types` → `{data:[{document_type, periodicity, allows_update}]}`; `GET .../documents/{id}` → detail plus `download_url`, an **expiring HMAC capability URL** to `GET .../documents/{id}/content?token=` (TTL `DOCUMENTS_URL_TTL_SECONDS`, default 600 s, hard max 3600; host from `DOCUMENTS_PUBLIC_BASE_URL`; `documents_url.py`) that a browser opens without headers; `GET .../documents/{id}/download` = authenticated stream. `POST .../documents/requests {document_type, year, month}` asks the backend to fetch a document, but **only the monthly federal-tax acuse has a fetch handler** (from ms-cfdis `fiscal_documents`); requests for the other seven types are persisted and stay `processing` indefinitely (`documents_fetch_handlers.py:10-26`). So constancia de situación fiscal and opinión de cumplimiento are not fetched by this API; if present they were uploaded through `POST .../documents` (perm `business:documents:upload`) or archived via sat_archives.
3. **Declaraciones — `GET /businesses/{b}/declaraciones?year=`** (perm `business:declaraciones:view`) → `{year, months:[{month, month_label, status, deadline, declarations:[{name, type, period_type:"monthly", status ∈ not_applicable|presented|future|upcoming|overdue, primary:{label, presentation_date, acuse_url, folio, importe_pagado}, complementarias:[...]}]}]}` (12 months always). ## 8. Constraints and pitfalls for an external MCP wrapper
1. **Token trust is inverted.** liebre-api accepts any JWT whose `email` claim matches a user, with no signature, expiry, issuer or audience check. The MCP must (a) perform real Auth0 verification itself before acting for a user, and (b) still forward **genuine Auth0-issued access tokens**, because ms-permissions and ms-cfdis receive the same token and may verify it; a token minted by the MCP would pass liebre-api but break every permission check (403/500) and every CFDI/SAT proxy. Design for the day JWKS verification is switched on: audience = the API identifier (`https://api-dev.liebre.ai/api/v1` in dev), scope `openid email`, `email` claim present. Confirm with the Auth0 tenant owner how `email` reaches access tokens and what the production tenant/audience are.
2. **Never use client-credentials (M2M) tokens for end-user traffic.** `@clients` subjects skip user lookup, permissions and business-access checks (only "firm exists" remains), so a single M2M token reads every firm; `GET /businesses` also rejects them with 400.
3. **Every business call needs `Accounting-Firm-ID`.** Resolve it per user with `GET /accounting_firms`, then `GET /businesses` per firm; keep a business → firm map (a business may belong to more than one firm). A wrong firm yields 403 (permission or business-access), not 404. Header spellings differ downstream (`Accounting-Firm-Id` to RAI, `X-Accounting-Firm-Id` to ms-cfdis) but the MCP only speaks to liebre-api.
4. Error mapping: 403 `Not authenticated` (missing bearer), 401 (undecodable token or unknown email), 400 (missing firm/permission headers, malformed fields), 404 (firm, business, period, JE not in that period), 403 `forbidden` envelope (permission denied or no business access), 409 (`expected_updated_at` mismatch, open review items, duplicate ids, DIOT destructive guards), 422 (business rules, invalid enum values, closed period).
5. Reports: pass `start_period_id` as a `YYYYMM` string and an optional `end_period_id`; handle `status: "processing"` by polling (payload rows are empty meanwhile); understand `include_pending_entries` (pending statuses are excluded from the JSON trial balance by default but included in exports by default) and `signed_balances`; a cold cache and the ms-permissions round trip (read timeout 120 s) add latency.
6. Binary outputs: reports, COA and JE exports are XLSX streams; CFDI PDF/XML, SAT-archive files and documents are streamed bytes; only `documents.download_url` is a shareable link and it expires after 10 minutes. The MCP has to download files and hand them to the client itself (or re-host them).
7. Volume: the JE list per period, the COA tree, statement lines and `bulk` are unpaginated and can be very large; `journal_entries/search` requires at least one filter and caps at 200. Add server-side summarization, projection and truncation in tools.
8. Writes: send the complete line set on PUT (omitted lines are deleted); always echo `updated_at` as `expected_updated_at`; unbalanced entries are accepted but demoted to `awaiting_validation`; the period must be open; `user_validated` needs `save_as_valid`; DELETE is a hard delete gated on `trashed`/`deleted`. Treat `renumber`, `from_template` PUT, `danger_zone`, period close/open, business delete, `cfdi_drafts/{id}/stamp`, autopilot PATCH/process, Syncfy connection changes and DIOT reset as irreversible or fiscally binding. Every JE write fans out asynchronously to RAI (embeddings, webhooks, translations).
9. Proxied surfaces (`cfdis/search`, DIOT rows, `cfdi_drafts`, `sat-account-classification`, autopilot, article 69-B, declaraciones F2) are untyped in OpenAPI and follow ms-cfdis/RAI contracts that change independently; wrap them loosely and expect 502/503 pass-throughs.
10. Nothing in this repo retrieves the constancia de situación fiscal or the opinión de cumplimiento; recently extracted SAT documents would be in `sat_archives` (structured `extracted_data` + files) or `documents` (uploaded). Verify on a live environment with `GET .../sat_archives/types` and `GET .../documents/types`; I ran nothing against dev.
11. Frontend deep links cannot be constructed from this repo; only the hosts (`app-dev.liebre.ai`, `app.liebre.ai`) are known. Check `ant-liebre-app` for route patterns.
12. Secrets hygiene to flag to the liebre team: `src/auth/validated_tokens.json` holds real (expired) dev JWTs with user emails, `main.py:506-508` hardcodes a Sentry DSN, and `GET .../digital_certificates` returns `storage_path`. Do not copy any of these into the MCP.
